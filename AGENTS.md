# AGENTS.md

Guidance for AI coding agents (and humans) working in this repository. `CLAUDE.md` imports this file, so this is the single source of truth.

## What Kargo is

Kargo is **Cargo for Kotlin**: a build tool and package manager written in Rust. One `kargo.toml` and one CLI (`kargo new`, `build`, `run`, `test`, `add`, `tree`, `package`, ...) build Kotlin projects for the **JVM, WebAssembly, Kotlin/Native and Android**.

Design points that shape most changes:

- **No Gradle for JVM, Wasm and Native.** Kargo downloads `kotlin-compiler-embeddable` / `kotlin-native-prebuilt` from Maven Central and drives the compilers directly. It can also download a Temurin JDK (`[toolchain] jdk = "21"`).
- **Android is the exception.** Kargo generates a Gradle project under `target/android` from `kargo.toml` and drives the Android Gradle Plugin. Users never write Gradle files.
- **Real Maven resolution** (POM inheritance, BOMs, exclusions, version ranges, relocations, Gradle module metadata) with Gradle-style conflict resolution (highest version wins unless `force = true`).
- **`kargo.lock`** pins every resolved version and the SHA-256 of every artifact.
- **Cargo-shaped UX**: Cargo-style status output, exit code 101 on build/test failure, `kargo <task>` and `kargo-<name>` subcommand plugins.
- **Built-in frameworks** (`[frameworks]`: serialization, coroutines, compose, ktor, lombok, spring-boot) contribute libraries, compiler plugins and compiler flags per target.

Users get the full picture from `README.md` and the website in `website/`. Read them before changing behavior.

Where things live when you need to change them:

- **A command or flag**: `src/cli.rs` (clap), implemented in `crates/kargo-ops/src/ops/<command>.rs`.
- **A `kargo.toml` key**: `crates/kargo-manifest/src/raw.rs` (all structs use `deny_unknown_fields`, so a new key must be added there), then the validated model in `lib.rs`, then `edit.rs` if `kargo add`/`remove` must write it, and the JSON Schema in `website/public/schemas/kargo.json` that editors use (`tests/schema.rs` checks every key it lists against the parser, and its enums and default versions against Kargo's).
- **`kargo metadata`** (the project model for editors): `crates/kargo-ops/src/ops/metadata.rs`. Its output is versioned (`FORMAT_VERSION`): add fields freely, but removing or redefining one needs a new version. `kargo lsp` and the JetBrains plugin's project import (`editors/jetbrains/.../project/KargoMetadata.kt`) read it.
- **`kargo lsp`** (the language server): `crates/kargo-lsp`. It reads the schema at `website/public/schemas/kargo.json` (compiled in) and builds on `kargo metadata`, so a field added there can be passed on to the Kotlin servers in `project.rs`. Its code actions edit through `ManifestEditor` and the split-out halves of the commands (`ops::add::add_to`, `ops::target::edit` and `scaffold_targets`), so keep a command and its action on the same code path. The servers themselves are downloaded and pinned in `crates/kargo-toolchain/src/language_server.rs`.
- **The JetBrains plugin**: `editors/jetbrains` (Kotlin; `./gradlew buildPlugin test`, needs JDK 21). It starts `kargo lsp` with the options in `lsp/KargoLanguageServerFactory.kt`, imports the project from `kargo metadata` (`project/`: `KargoMetadata` reads the fields, `KargoImportPlanner` maps them to modules and libraries, `KargoProjectImporter` applies them, and `KotlinSupport` is the only code that touches the Kotlin plugin's internal facet and library-kind classes, so check `./gradlew verifyPlugin -PverifyIde=<newest IDE>` after changing it), and uses `kargo/runnables`, the `kargo/*` commands and `kargo test --message-format json`, so when you change one of those, check the plugin still reads it. Its guide is the IntelliJ IDEA and Android Studio section of `guides/editors.md`.
- **The Zed extension**: `editors/zed` (Rust; `cargo test` and `cargo build --release --target wasm32-wasip2` there). It runs `kargo lsp` (with `checkOnSave` on), `kargo dap` with the launch configuration in `debug_adapter_schemas/Kargo.json`, and `kargo metadata --no-deps`; its run buttons use the tasks `kargo ide --zed` writes (`crates/kargo-lsp/src/zed.rs`) with the tags of Zed's Kotlin extension. When you change those commands or `kargo dap`'s launch arguments, check the extension still matches. Its guide is the Zed section of `guides/editors.md`.
- **The Neovim plugin**: `editors/neovim` (Lua; `nvim --headless -u NONE -l tests/run.lua` there). `lsp/kargo.lua` is the server config Neovim 0.11 reads from the plugin, `lua/kargo/` holds `:Kargo` (`init.lua`), the JSON message decoding that its quickfix list and diagnostics use (`messages.lua`, which reads `--message-format json` output, so check it when those messages change) and the nvim-dap setup (`dap.lua`, over `kargo dap`), and `lua/neotest-kargo/` the neotest adapter (`scan.lua` finds the tests of a Kotlin file by reading its lines). The tests stub neotest, so they run without it. Its guide is the Neovim section of `guides/editors.md`.
- **The Emacs package**: `editors/emacs` (Emacs Lisp; `emacs -Q --batch -L . -l test/kargo-tests.el -f ert-run-tests-batch-and-exit` there). `kargo.el` runs each command through `compilation-start` in `kargo-compilation-mode`, with `--message-format json` for `build`, `check`, `run` and `test`; `kargo--filter` turns those JSON lines (`kargo-messages.el`, which reads `--message-format json` output, so check it when those messages change) into `file:line:column: error:` lines that `next-error` follows, and the frames of a failed test's stack trace into links. `kargo-test.el` finds tests by reading Kotlin sources and keeps the results of the last run, `kargo-eglot.el` and `lsp-kargo.el` start `kargo lsp` and ask it for `kargo/runnables`, `kargo-flymake.el` keeps the diagnostics of the last build for Flymake, and `kargo-dape.el` runs `kargo dap` (its launch arguments are `args`, `cwd` and `env`). When you change those commands, the JSON messages or `kargo dap`'s launch arguments, check the package still matches. Its guide is the Emacs section of `guides/editors.md`.
- **The VS Code extension**: `editors/vscode` (TypeScript). The pure modules (`commands.ts`, `diagnostics.ts`, `executable.ts`, `kotlinScan.ts`, `maven.ts`, `messages.ts`, `metadata.ts`, `process.ts`) have no `vscode` import, so `npm test` runs their unit tests in `src/test/`; `npm run test:integration` runs `src/integration/` in VS Code 1.100 on a new `kargo new` project, so run it after changing the extension's behavior. `servers.ts` starts `kargo lsp` per folder with a `kargo.toml`, `tasks.ts` runs the `kargo` tasks and reads their compiler messages, `testing.ts` is the test explorer (`kargo test --list --format json`, `--message-format json`), `codeLens.ts` the Run and Debug buttons, `debug.ts` runs `kargo dap`, and `actions.ts` the commands. Every command line is built in `commands.ts`, and `metadata.ts` reads `kargo metadata --no-deps`. Kotlin's highlighting is the TextMate grammar in `syntaxes/kotlin.tmLanguage.json`, since `kargo lsp` sends no semantic tokens; `kotlinGrammar.test.ts` checks its scopes. When you change those commands, the JSON messages or `kargo dap`'s launch arguments, check the extension still matches. Its guide is the Visual Studio Code section of `guides/editors.md`.
- **Kargo's own Kotlin server** (`kargo lsp --server kargo`, the default; IntelliJ keeps `--server none`): `crates/kargo-lsp/src/kotlin`. It runs in-process behind `server.rs` like any other backend. It reads the project from `kargo metadata --no-deps` (`kotlin/server.rs`, `Model`: source roots per package, set and target), so a change to source layout or metadata must keep `model_from_metadata` right. Its tests run against the outline of the standard library in `stubs.kt`; `KOTLIN_SOURCES=<extracted stdlib sources> cargo test -p kargo-lsp -- --ignored` runs them against the real one. Its code actions (`kotlin/actions.rs`) add dependencies through `kargo/addDependency`, which `kargo lsp` runs itself, so they share that command's code path; the packages they know a Maven module for are `KNOWN_PACKAGES` there. `textDocument/formatting` runs ktlint on a worker thread (`State::format`, answered by `Event::Formatted`; `ktlint_formatter` in `kotlin/server.rs`) through `ops::fmt::format_text`, the stdin mode of what `kargo fmt` runs, so keep the two on the same ktlint, JDK and `[fmt]` settings. `kotlin/server.rs` has a `Hub` with one `State` per workspace folder: file messages go to the deepest root above the file (`Hub::route`), workspace symbols fan out to all (`FanOut`), each state's events and output reach the hub through `Tx` (`Event::For`, `Event::Out`) and the ids of its requests to the editor are `kotlin/<project>/<n>`. References, rename and `workspace/symbol` run through `State::search` on a worker (cancelled by `$/cancelRequest`), the load reports `$/progress` (`State::loading`, ended by `Event::Loaded`), an editor without file watchers gets `State::rescan` on save and every `RESCAN_INTERVAL`, and `text.rs` holds the negotiated position encoding (`text::encoding`, UTF-8 or UTF-16), so compute columns with `text::position`/`offset`, never `len_utf16`. Its guide is `guides/kotlin-server.md`.
- **Kotlin scripts** (`kargo script`): the `@file:` header of a `.kts` file and the `/* kargo ... */` front matter of a `.kt` file are read in `crates/kargo-manifest/src/script.rs`; `crates/kargo-ops/src/script.rs` resolves, compiles, caches and runs them (the first run of a `.kts` script runs inside the Kotlin compiler, later runs start the cached classes with `java`); the language server's completion, hover and diagnostics for them are `crates/kargo-lsp/src/script.rs`. Its guide is `guides/scripts.md`.
- **The debug adapter** (`kargo dap`): `crates/kargo-lsp/src/dap.rs`. kotlin-debug-adapter is pinned in `language_server.rs` (`KDA_VERSION`, `KDA_SHA256`).
- **C interop of the Native target**: the `[target.native]` and `cinterop` keys in `crates/kargo-manifest/src/raw.rs` (`NativeOptions`, `Cinterop`, `CSources` in `lib.rs`); the `cinterop`, `konanc` and clang command lines, the generated `.def` file and the hints for missing headers and symbols in `crates/kargo-compiler/src/native.rs` (`CinteropUnit`, `NativeCompilation`, `CSourcesUnit`); per-platform options, pkg-config, `link = "static"`, C source files and `export` in `crates/kargo-ops/src/native_interop.rs`; the `.pc` reader in `crates/kargo-ops/src/pkg_config.rs`; XCFrameworks in `create_xcframework` (`ops/build.rs`). Its guide is `guides/c-interop.md`.
- **Wasm output and browser support**: compiler flags in `crates/kargo-compiler/src/wasm.rs`; the page of a browser app, the import map for npm packages, a library's `package.json`, `wasm-opt` and the size report in `crates/kargo-ops/src/wasm_output.rs`; the loopback server behind `kargo run` and the browser test page in `crates/kargo-ops/src/web.rs`; browser lookup in `crates/kargo-toolchain/src/browser.rs`; npm installs in `crates/kargo-ops/src/npm.rs`; Kotlin declarations for npm packages in `crates/kargo-ops/src/dts/` (`program.rs` finds and reads the `.d.ts` files, `parser.rs` parses them, `kotlin.rs` writes the `external` declarations; bump `dts::FORMAT` when the output changes), generated by `npm::declarations` before each Wasm compilation and by `kargo lsp` on load.
- **A built-in framework**: `crates/kargo-ops/src/builtins.rs`; project templates for `kargo new` are in `crates/kargo-ops/src/ops/new.rs`.
- **Code generation** (`[[generate]]`, `kargo generate`, `target/generated/`): the keys are `RawGenerate` and `validate_generators` in `crates/kargo-manifest/src/raw.rs` (`Generator`, `GeneratorAction` in `lib.rs`); `crates/kargo-ops/src/generate.rs` plans the steps (`after`), skips the ones whose hash of inputs and definition is unchanged (`run_step`, `fingerprint`, `input_files`), writes a step into an empty directory and then keeps the old file of every file whose bytes did not change (`begin`, `finish`, so the compilers' mtime checks stay quiet), and runs `run`, `tool` (resolved as `generate/<name>` in `kargo.lock`), `build-config` and `protobuf` (`protoc` and the gRPC plugins from Maven classifiers; the grpc-kotlin plugin is a jar, so `jar_launcher` writes a script for it). `ensure` runs the steps of a target once per invocation (guarded with `BuildContext::built_artifact`, so path dependencies and parallel targets share it) and `ops::build::sources` calls it; `existing_sources` does not, so `kargo metadata` never runs a step. The output directories are in the `source-roots`, `test-roots` and `resource-roots` of `kargo metadata` and in its `generated-roots`; `kargo lsp` (`model_from_metadata`) and the JetBrains planner (`contents` in `KargoImportPlan.kt`, since a root inside the excluded `target/` is not indexed) read them; `gradle.rs` adds them to the Android source sets (`GeneratedDirs`). The `protoc` and gRPC plugin versions are `PROTOC_VERSION`, `GRPC_JAVA_VERSION` and `GRPC_KOTLIN_VERSION` in `generate.rs`. Its guide is `guides/code-generation.md`.
- **Benchmarks** (`kargo bench`, `benches/`, `benches-<target>/`, `[bench]`, `[frameworks] benchmark`): the flags in `src/cli.rs` (`Command::Bench`; `bench_profile` picks `release` or `[profile.bench]`); `crates/kargo-ops/src/ops/bench.rs` compiles `benches/` like the tests (`compile_benches`, against the `jvm/bench` resolution that adds kotlinx-benchmark and JMH, with the `allopen` plugin for JMH's `@State`), runs JMH's bytecode generator in its `reflection` mode (`generate_harness`, from the `jvm/bench-tools` resolution; ASM mode fails on the newest class file versions) and compiles what it writes with `javac`, then runs `org.openjdk.jmh.Main` with the options `settings` and `jmh_args` compute (flags, then `[bench]`, then an annotation in the sources, then Kargo's defaults); `crates/kargo-ops/src/bench.rs` reads JMH's JSON, compares runs with Welch's t-test and prints the table; the versions are `KOTLINX_BENCHMARK_VERSION` and `JMH_VERSION` in `builtins.rs`, and the `[bench]` keys are `BenchSettings` in `kargo-manifest`. Only the JVM target runs benchmarks. Baselines are `target/bench/<name>.json`. Its guide is `guides/benchmarking.md`.
- **Watch mode** (`run --watch`, `test --watch`, `kargo watch`): the flags and the loops in `src/cli.rs`; the watched files and the loop that runs a step again on each change in `crates/kargo-ops/src/ops/watch.rs`; the polling watcher in `crates/kargo-util/src/watch.rs`; `start` and `Running` in `ops/run.rs` build the program and keep it running across rebuilds.
- **JVM application formats** (`kargo package --format jlink|native-image|installer`, `kargo run --native-agent`): the `[package.jlink]`, `[package.native-image]` and `[package.installer]` keys are `PackagingSettings` in `crates/kargo-manifest/src/lib.rs`; the runtime image, launchers, `native-image` and `jpackage` command lines in `crates/kargo-ops/src/ops/packaging.rs`, dispatched from `package` in `ops/mod.rs`; `[toolchain] graalvm`, GraalVM installs (foojay Disco API) and the reachability metadata repository in `crates/kargo-toolchain/src/graalvm.rs`; the tracing agent in `ops/run.rs`. Its guide is `guides/distributing.md`.
- **Installing tools** (`kargo install`, `kargo uninstall`): `crates/kargo-ops/src/ops/install.rs`. It builds the program with `ops::package` (JVM) or `ops::build::build` (Native), or resolves it from Maven, and `commit` copies it to `~/.kargo/bin` (launchers) and `~/.kargo/install/<name>/<version>/`, recording it in `.installed.toml` (`Layout` picks the directories; `--root` / `KARGO_INSTALL_ROOT` move them). The launcher helpers are shared with `ops/packaging.rs`, and the `kargo.main-class` POM property that Maven installs read is written by `publication.rs`. Its guide is `guides/installing-tools.md`.
- **Compose Desktop and Compose resources** (`kargo package --desktop`, `--platforms`, `composeResources/`): the Skiko native jars, `-Dskiko.library.path`, the JDK modules and `kargo run`'s Dock options in `crates/kargo-ops/src/compose/mod.rs`; the `Res` generator (directory qualifiers, `.cvr` string files, the Kotlin accessors) in `compose/resources.rs`, called from `sources()` in `ops/build.rs` (JVM), `gradle.rs` (Android, as assets) and `ops/metadata.rs` (the `compose-resources` field the Kotlin server reads); `file-associations` and `notarize` of `[package.installer]` in `ops/packaging.rs`. Its guide is `guides/compose.md`.
- **Releases, installers and `kargo self`**: `.github/workflows/release.yml` builds eight targets on a `v<version>` tag and publishes `kargo-<version>-<target>.tar.gz` (`.zip` on Windows), `SHA256SUMS` and `VERSION`. The names are fixed in `archive_name` (`crates/kargo-ops/src/ops/self_update.rs`, which also has the release URL layout, the package manager detection, the replace-the-running-binary logic and the once-a-day notice of `kargo --version`) and repeated in `website/public/install.sh`, `install.ps1`, the `[package.metadata.binstall]` of `Cargo.toml` and `packaging/`; change them together. `crates/kargo-ops/build.rs` exports the build target as `KARGO_TARGET`. `KARGO_RELEASES_URL` (a URL or `file://` directory) makes all of it testable offline: `tests/self_update.rs` publishes fake releases to a temp directory. `[toolchain] kargo` (a semver requirement, checked against the running version in `raw.rs`) is the minimum Kargo version of a project; `kargo self` never loads a manifest. User-facing text: `getting-started/installation.md`, `reference/commands.md` (`kargo self`), `reference/contributing.md` (Releases).
- **CI workflows** (`kargo init-ci`): `crates/kargo-ops/src/ops/ci.rs` reads the packages' `[toolchain] jdk` and targets into a `CiPlan` and writes the workflow text; the composite action it uses is `setup-kargo/action.yml` (installs with `website/public/install.sh` / `install.ps1`, caches the Kargo home without `daemon/`). Its guide is `guides/ci.md`.
- **Importing a project** (`kargo import`): `crates/kargo-ops/src/ops/import/`. `mod.rs` detects the build tool, plans (`plan`: builds every `kargo.toml`, parses each with the real manifest loader, plans every file move) and applies (`apply`) the import, and prints the report (`Note`: translated, or in need of manual work with a docs link). `model.rs` is the build-tool-independent model (`Package`, `Dependency`, `Frameworks`) and the writer of `kargo.toml`, so a new manifest key the importer should write goes there. `maven.rs` reads `pom.xml` with `kargo_maven::pom` (parents, properties, management) plus the `<build>` plugins, repositories and modules; `gradle/` reads Gradle scripts without running Gradle (`dsl.rs` the Kotlin/Groovy reader and string evaluator, `catalog.rs` version catalogs, `dependencies.rs` configurations and notations, `sources.rs` source sets and where their files go, `mod.rs` plugins, targets and the translation). `frameworks.rs` turns the libraries and plugins of a framework into `[frameworks]` entries and takes the dependencies the framework adds out of the lists, so keep it in step with `builtins.rs` when a framework's dependencies change. `layout.rs` expands the directory moves into file moves and does them (`git mv` in a repository). Its guide is `guides/importing.md`.
- **Dependency resolution**: `crates/kargo-maven/src/resolver.rs`; locking in `crates/kargo-ops/src/lockfile.rs`.
- **Offline and corporate builds** (`kargo vendor`, `--vendored`, `~/.kargo/config.toml` and `.kargo/config.toml`): the files are read in `crates/kargo-util/src/settings.rs` (`Settings::load`, called from `with_settings` in `src/cli.rs`, which also picks the vendor directory); every HTTP client is built by `kargo_util::http::agent` (proxy and `[http] cainfo`); `effective_repositories` in `crates/kargo-maven/src/repo.rs` applies `[mirrors]` and `--vendored` inside `MavenClient::new`, which keeps the declared repositories for the `kargo.lock` fingerprint (`declared_repositories`) and records what it served (`served_files`); `[toolchain-mirrors]` is applied in `crates/kargo-toolchain/src/download.rs`; the Android `settings.gradle.kts` mirrors in `settings_gradle_with` (`gradle.rs`); `kargo vendor` is `crates/kargo-ops/src/ops/vendor.rs`. Its guide is `guides/offline-and-mirrors.md`.
- **Publishing** (`kargo publish`): the command in `crates/kargo-ops/src/ops/publish.rs`; the modules, POMs and `.module` files in `crates/kargo-ops/src/publication.rs`; GnuPG signing in `crates/kargo-ops/src/signing.rs`; uploads to repositories in `crates/kargo-maven/src/deploy.rs`; the Maven Central Portal in `crates/kargo-maven/src/central.rs`.
- **Source-layout conventions** (`src/`, `src-<target>/`, `tests-<target>/`, `benches-<target>/`, `resources/`, `android/`): `crates/kargo-ops/src/workspace.rs`.
- **The project environment** (`[env]` and `[profile.<name>.env]`, `.env` files, `--env-file`): the resolver and the dotenv parser in `crates/kargo-ops/src/env.rs`, `kargo env` in `crates/kargo-ops/src/ops/env.rs`. Programs get it through `BuildContext::project_env`, which checks `required`; `hook_env` passes the variables to hooks without that check. `BuildContext::program_env_applies` says which targets get it. The generated `BuildConfig` of `[env] expose` is written in `add_build_config` (`crates/kargo-ops/src/ops/build.rs`), which `sources()` calls.
- **A warning about a valid but suspicious project** (no sources, ignored `.kts`, a task hidden by a built-in command, an odd version): `crates/kargo-ops/src/warnings.rs`. Source checks run from `ops/build.rs` (`warn_about_sources`, also used by `check` and `package`; `test` reports only ignored files), manifest checks from `warn_manifest` in `src/cli.rs`. List each warning in `website/src/content/docs/reference/warnings.md`.
- **Compiler output** (relaying, `--message-format json` and its `target` field, the order of the `-Werror` summary): `crates/kargo-compiler/src/diagnostics.rs`; `kargo lsp` turns it into editor diagnostics in `crates/kargo-lsp/src/check.rs`.
- **Workspaces and path dependencies**: `Project` in `crates/kargo-ops/src/workspace.rs` loads members and path dependencies (a `Workspace` there is one package); `BuildContext::for_package` and `local_dependencies` in `ops/context.rs` share state between packages; `ops/local.rs` builds dependency jars and klibs.

## Build, test, format

```sh
cargo build
cargo test --workspace                       # unit + CLI integration tests; offline, no JDK needed
cargo fmt --all                              # always before finishing; rustfmt.toml sets max_width = 140
cargo clippy --workspace --all-targets       # don't introduce new warnings

KARGO_E2E=1 cargo test --test e2e            # real compilers: JVM, Wasm, Spring, Ktor, Compose, pinned JDK
KARGO_E2E=1 KARGO_E2E_NATIVE=1 KARGO_E2E_ANDROID=1 cargo test --test e2e   # also Native and Android (slow)
```

The default `cargo test` must never need network access or a JDK. The e2e tests are gated behind `KARGO_E2E`.

## Code conventions

Match the surrounding code. In particular:

- **Errors**: `anyhow::Result` with `.context(...)` / `bail!`. `thiserror` is used only in `kargo-maven`. Error messages are plain lowercase sentences that tell the user what to do next. `cli.rs` prints the cause chain and exits with 101.
- **Output**: user-facing status goes through `kargo_util::shell::Shell` (`status("Compiling", ...)`, `note`, `error`; stderr, honoring `-q`/`-v`). Only the program or test output of `kargo run` / `kargo test` goes to stdout. Don't `println!` from library crates.
- **Docs in code**: every module starts with a `//!` comment; public items get `///` where the name alone is not enough.
- **Cross-platform**: Kargo runs on Windows, macOS and Linux. Use `std::path`, the helpers in `kargo-util`, and avoid shell-specific assumptions. Files use LF line endings (`.gitattributes`).
- **Pinned versions** live in constants (`DEFAULT_KOTLIN_VERSION`, `DEFAULT_JVM_TARGET` in `kargo-manifest`; the `*_VERSION` constants in `builtins.rs` and `gradle.rs`; the tool versions `DOKKA_VERSION`, `KTLINT_VERSION` and `DETEKT_VERSION` in `ops/doc.rs`, `ops/fmt.rs` and `ops/lint.rs`; the language servers' `KOTLIN_LSP_VERSION`, `KLS_VERSION` and `KLS_SHA256`, and the debug adapter's `KDA_VERSION` and `KDA_SHA256`, in `kargo-toolchain`'s `language_server.rs`; the GraalVM reachability metadata repository's `REACHABILITY_METADATA_VERSION` and `REACHABILITY_METADATA_SHA256` in `graalvm.rs`). Don't hard-code a version elsewhere in Rust code.
- **Unknown `kargo.toml` keys are errors**, by design. Keep it that way.

## Tests

- Unit tests sit next to the code in `#[cfg(test)] mod tests` (`kargo-manifest` keeps them in `src/tests.rs`).
- New CLI behavior gets a test in `tests/cli.rs`. Use `tests/common`: `Project` (scratch directory with an isolated `KARGO_HOME`) and `LocalRepo` (an on-disk `file://` Maven repository), so the test stays offline.
- Behavior that depends on a real Kotlin compiler gets an e2e test in `tests/e2e.rs`, behind `require_e2e!()`.
- Fix a bug by adding a test that fails without the fix.

## Documentation is part of the change

**Every change that affects what a user sees, types, configures or gets must update the documentation in the same change.** That means commands, flags, aliases and their output; `kargo.toml` keys and defaults; frameworks; environment variables; the lockfile; the project layout; toolchains; tasks and plugins; target behavior; error messages worth explaining; and default versions.

The docs are two things that must stay consistent:

1. **The website**, in `website/src/content/docs/` (Markdown, rendered by Starlight). This is the full documentation.
2. **`README.md`**, which mirrors the headline content: the command table, `kargo.toml` overview, project layout, environment table and the crate table. Update its matching section whenever you update the website page for the same thing.

Refactors, internal tests and performance work with no visible effect don't need docs. Say so in your summary rather than leaving it implicit.

### When no page fits: add one

If the change introduces something the existing pages don't cover (a new framework, a new target, a new workflow), create a new page rather than stretching an unrelated one.

1. **Pick the section.** `guides/` for task-oriented how-tos, `reference/` for exhaustive lookups, `getting-started/` for onboarding, `migration/` for comparisons with other tools.
2. **Create** `website/src/content/docs/<section>/<slug>.md` with this frontmatter (both fields are required):
   ```md
   ---
   title: Short page title
   description: One sentence on what the reader will learn or find.
   ---
   ```
3. **Add it to the sidebar** in `website/astro.config.mjs`, in the matching group: `{ label: 'Short title', slug: '<section>/<slug>' }`. The slug has no extension and no leading slash. Pages not in the sidebar are effectively hidden.
4. **Link it** from the related pages (and from `reference/commands.md` or `reference/manifest.md` when it documents a command or key).
5. Add a card or link on `index.mdx` only if it is a headline feature.

### Writing style

Follow the existing pages:

- Second person, present tense, short paragraphs. Show a working example first, then explain the options.
- Code fences: `sh` for commands to run; `console` with `$ ` prompts when showing a command and its output; `toml title="kargo.toml"`, `kotlin title="src/Main.kt"` and similar for files. Use tables for key and flag references.
- Asides: `:::note`, `:::tip`, `:::caution` (Starlight syntax).
- Internal links are relative with a trailing slash, e.g. `[Frameworks](../frameworks/)` or `[Commands](../../reference/commands/)`. The site is served under a base path on GitHub Pages, so never use root-absolute links like `/guides/...`.
- Every command, flag, key and output in the docs must be real. Check with `kargo <command> --help` and by running the example instead of writing it from memory.

### Verify the site builds

```sh
cd website
bun install          # first time only
bun run build        # must succeed; output goes to website/dist
bun run dev          # optional: preview at http://localhost:4321/
```

Fix any build error (bad frontmatter, a sidebar slug that doesn't match a file) before finishing. `website/dist`, `.astro` and `node_modules` are gitignored.

## Finishing a task

Before reporting a task as done:

1. `cargo fmt --all` and `cargo test --workspace` pass (run the e2e tests too when you touched compiler drivers, frameworks or toolchains).
2. The docs are updated per the section above, and `bun run build` in `website/` passes if you touched `website/`.
3. Your summary lists which docs pages you changed or created, or states why none were needed.
