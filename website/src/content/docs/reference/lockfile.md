---
title: kargo.lock
description: What kargo.lock contains and how it keeps builds reproducible and safe.
---

`kargo.lock` is written by Kargo after resolving dependencies. **Commit it** for applications and libraries alike: it makes builds reproducible and detects tampered downloads.

## What it records

For every resolution (one per target and classpath, such as `jvm/runtime`):

- a fingerprint of the inputs (requested dependencies, BOMs, repositories),
- the root modules,
- every resolved module with its version and the dependencies it asked for,
- the repository path and **SHA-256** of every downloaded file.

```toml title="kargo.lock"
# This file is automatically generated by Kargo.
# It is not intended for manual editing.
version = 1

[resolution."jvm/runtime"]
inputs = "4f9c..."
roots = ["org.jetbrains.kotlinx:kotlinx-datetime"]

[[resolution."jvm/runtime".package]]
module = "org.jetbrains.kotlinx:kotlinx-datetime-jvm"
version = "0.7.1"
dependencies = ["org.jetbrains.kotlin:kotlin-stdlib:2.1.20"]

[[resolution."jvm/runtime".package.files]]
path = "org/jetbrains/kotlinx/kotlinx-datetime-jvm/0.7.1/kotlinx-datetime-jvm-0.7.1.jar"
sha256 = "b3a1..."
```

## How it's used

- If the inputs of a resolution haven't changed, Kargo reuses the locked result without touching the network for metadata.
- Missing files are re-downloaded and **checked against the locked SHA-256**. A mismatch is an error.
- Downloads are also checked against the repository's `.sha1` files.
- Before an artifact's hash is written to the lockfile, a file that was already in `~/.kargo/cache/maven` is checked against the repository's `.sha1` too. A corrupt cached file (for example, left by an interrupted download) is downloaded again, so a bad file is never locked.
- When you change dependencies in `kargo.toml`, only the affected resolutions are recomputed.
- The file is only rewritten when its content changes.

## SNAPSHOT versions

A SNAPSHOT keeps its version (`1.0-SNAPSHOT`), but the files it locks have the timestamped names the repository stores, so the lockfile records which build you use:

```toml title="kargo.lock"
[[resolution."jvm/runtime".package]]
module = "com.acme:lib"
version = "1.0-SNAPSHOT"

[[resolution."jvm/runtime".package.files]]
path = "com/acme/lib/1.0-SNAPSHOT/lib-1.0-20240101.120000-1.jar"
sha256 = "9d2e..."
```

The build stays locked until `kargo update` (which prints `Updating com.acme:lib v1.0-SNAPSHOT (20240101.120000-1) -> v1.0-SNAPSHOT (20240102.080000-2)`) or `--refresh` picks a newer one. A selective `kargo update <group:artifact>` keeps every other SNAPSHOT on its locked build. See [SNAPSHOT versions](../../guides/dependencies/#snapshot-versions).

## Workspaces and path dependencies

Packages built together share one `kargo.lock`: the workspace's, at its root, or the consuming package's when it has [path dependencies](../../guides/workspaces/) outside a workspace. Each package's resolutions are keyed with its name, such as `mathlib/jvm/runtime`. Outside a workspace, the consuming package keeps the plain keys (`jvm/runtime`). `kargo update` re-resolves every package of the project.

### Checksum mismatches

When a re-downloaded file doesn't match `kargo.lock`, the error says which side is suspect:

- If the downloaded file matches the checksum the repository publishes, the **lockfile entry** is likely wrong, for example because it was recorded from a corrupt cached file. If you trust the repository, run `kargo update` to re-lock it.
- If the repository publishes no checksum, Kargo can't tell: the artifact may have changed upstream or been tampered with, or the lockfile entry may be wrong. Investigate before running `kargo update`.

## Commands

| Command | Effect |
|---|---|
| `kargo update` | Re-resolve everything and rewrite the lockfile (picks up new versions within ranges and the newest build of each SNAPSHOT) |
| `kargo update <group:artifact>...` | Re-resolve only these modules; every other module keeps its locked version |
| `kargo update <group:artifact> --precise <version>` | Lock one module at exactly this version. It stays locked until `kargo.toml` changes or you update that module again |
| `kargo update --dry-run` | Print what would change (`Updating`, `Adding`, `Removing`) without writing the lockfile |
| `--locked` | Fail if the lockfile would change. Use it in CI. |
| `--refresh` | Ignore the lockfile and cached metadata for this run, and re-verify cached artifacts against the repository (re-downloading corrupt ones) |

If the lockfile is corrupt or from an unsupported version, delete it; Kargo regenerates it on the next build.
